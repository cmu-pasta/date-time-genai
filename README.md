# DateTime GenAI Testing Framework (dt-fuzz)

A differential fuzz testing framework designed to measure the **reliability** and **consistency** of LLM-generated date/time code through automated testing and analysis.

## Overview

As LLMs are increasingly integrated into software development workflows, with a growing proportion of production code being generated entirely by AI assistants, a critical question emerges: **Do LLMs make it easier to write correct date/time code?**

This framework investigates this question by conducting systematic experiments to study the robustness of LLM-generated date/time code. Since there is no automated way to assess the *correctness* of code generated for an arbitrary task, we measure **reliability** (consistency across repeated prompting for the same task) and **cross-library consistency** (semantic equivalence when using different date/time libraries).

**dt-fuzz** uses state-of-the-art LLMs to automatically generate datetime computation tasks and corresponding code implementations, then performs differential fuzz testing to reveal discrepancies and subtle behavioral differences that may evade superficial code review.

### Research Motivation

Date/time computations are notoriously error-prone due to complexities like time zones, daylight saving time, leap years, and varying calendar systems. This framework reveals that even simple date/time tasks can conceal subtle pitfalls when generated by LLMs, with code pairs that appear identical exhibiting divergent behavior on edge-case inputs.

### Key Findings at a Glance

Our experiments with GPT-5, Claude Sonnet 4, and Gemini 2.5 Flash reveal:

- **📊 No perfect reliability**: 15-28% of code pairs from the same LLM differ in behavior
- **👁️ Deceptive similarity**: 7-11% of pairs appear identical but fail on edge cases  
- **📚 Library understanding gaps**: 58-64% error rate when generating code for non-standard libraries
- **📝 Underspecified prompts**: 33.33% of behavioral differences stem from ambiguous requirements
- **✅ Testing is essential**: Visual inspection is insufficient—comprehensive testing catches hidden bugs

**Bottom Line**: LLMs can generate syntactically correct date/time code, but semantic correctness requires explicit requirements, comprehensive testing, and careful validation.

## Architecture

The framework follows a five-stage pipeline:

1. **Task Generation**: LLM generates N=100 diverse datetime computation tasks (intentionally kept small to model realistic developer interactions). Tasks are language-agnostic and specify date/time logic without implementation details. Example: "Find the number of days between two given datetimes."

2. **Code Generation**: For each task, the LLM produces code snippet pairs:
   - **For Reliability Testing**: C₁ and C₂ both using Python's `datetime` library (independent samples)
   - **For Consistency Testing**: C₁ using `datetime` library, C₂ using `pendulum` library
   - All code must accept typed inputs and produce ISO 8601-compliant output

3. **Test Harness Creation**: The framework parses LLM outputs, extracts type information, and embeds code into predefined test templates with appropriate input generators and output logging

4. **Random Fuzzing**: Each code pair executes with I=10,000 deterministically generated inputs (using fixed seed for reproducibility). Outputs are serialized and logged sequentially

5. **Differential Testing & Analysis**: 
   - Compares output logs to identify behavioral differences
   - Categorizes results as: Non-differentiating, Differentiating (with percentage P), or Program Error

## Installation

### Prerequisites

- Python 3.12 or higher
- Poetry (Python package manager)

### Setup

1. Clone the repository:
```bash
git clone <repository-url>
cd datetime_genai
```

2. Install dependencies using Poetry:
```bash
poetry install
```

3. Create a `.env` file with your API keys:
```bash
# Only set keys for models you plan to use
OPENAI_API_KEY=your_openai_key
ANTHROPIC_API_KEY=your_anthropic_key
GEMINI_API_KEY=your_gemini_key
```

## Usage

The framework is controlled through the `run.py` script with various command-line options.

### Quick Start

Run the complete pipeline for a specific model:

```bash
python run.py --model openai --all
```

### Step-by-Step Execution

Execute individual stages:

```bash
# Generate datetime computation ideas
python run.py --model claude --ideas

# Generate datetime library code snippets
python run.py --model gemini --dt-code

# Generate pendulum library code snippets
python run.py --model gemini --pd-code

# Create differential tests
python run.py --model openai --create-tests

# Run the tests
python run.py --model openai --run-tests

# Analyze results and generate reports
python run.py --model openai --analyze
```

### Combined Operations

Chain multiple stages together:

```bash
# Generate ideas and code
python run.py --model claude --ideas --dt-code --pd-code

# Create and run tests
python run.py --model openai --create-tests --run-tests

# Generate all code types
python run.py --model gemini --dt-code --pd-code
```

### Available Models

The framework supports three state-of-the-art LLMs evaluated in the research:

- `openai` - GPT-5 (most widely adopted LLM provider)

## How It Works

### Differential Testing Approach

The framework generates multiple independent implementations of the same datetime computation and compares their outputs:

1. **DateTime vs DateTime**: Two independent implementations using Python's `datetime` library
   - Tests the **reliability** of LLM-generated code
   - Identifies inconsistencies in AI-generated implementations

2. **DateTime vs Pendulum**: Implementations in different datetime libraries
   - Tests for **semantic equivalence** across libraries
   - Discovers library-specific behaviors and edge cases

## Research Findings

This section summarizes key experimental results from testing three state-of-the-art LLMs: GPT-5 (OpenAI), Claude Sonnet 4 (Anthropic), and Gemini 2.5 Flash (Google).

### Experimental Setup

- **Tasks (N)**: 100 datetime computation tasks
- **Test Inputs (I)**: 10,000 randomly generated inputs per code pair
- **Language**: Python only
- **Libraries**: Python `datetime` (standard) and `pendulum`
- **Models**: GPT-5, Claude Sonnet 4, Gemini 2.5 Flash

### 1. Reliability of LLM-Generated Date/Time Code

**Reliability testing** evaluates LLM consistency by generating code pairs where both C₁ and C₂ use the same library (`datetime`), but are produced from separate, identical queries to the same LLM.

#### Results Summary

| LLM Model | Program Error | Non-Differentiating | Differentiating | Deceptively Similar (P < 75%) |
|-----------|--------------|---------------------|-----------------|-------------------------------|
| GPT-5 | 47% | 38% | 15% | 7% |
| Claude Sonnet 4 | 40% | 32% | 28% | 11% |
| Gemini 2.5 Flash | 48% | 34% | 18% | 7% |

#### Key Observations

- **No model achieves perfect reliability**: All models generate code pairs with behavioral inconsistencies
- **Deceptive similarity**: A substantial proportion of differentiating pairs appear nearly identical but disagree on specific edge cases
- **Subtle divergences**: Many pairs disagree on less than 75% of inputs, making differences difficult to detect during code review
- **Variability in disagreement rates**: Different tasks exhibit varying degrees of input disagreement

#### Example: Subtle "Off-by-One" Error

Consider the task: "Find the number of days between two given datetimes."

Two implementations that appear identical produce different outputs for 24.59% of test cases. For inputs `2004-08-29T09:04:24.391178` and `1971-07-07T23:46:54.870955`:
- **Datetime**: Reports `⟨-12107 days, 52950 seconds⟩`
- **Pendulum**: Reports `⟨-12106 days, -33449 seconds⟩`

This occurs because `datetime` enforces canonical form (non-negative seconds) while `pendulum` allows negative seconds for "intuitive" representation.

> **Insight**: LLM-generated date/time code pairs that appear identical can still differ on edge case inputs. Developers must go beyond visual inspection and rely on semantic analysis and comprehensive testing to ensure correctness.

### 2. Cross-Library Consistency of LLM-Generated Date/Time Code

**Consistency testing** measures how well LLMs maintain semantic equivalence when generating code for different date/time libraries. Code pairs use `datetime` (C₁) vs `pendulum` (C₂) for the same task.

#### Results Summary

| LLM Model | Program Error | Non-Differentiating | Differentiating |
|-----------|--------------|---------------------|-----------------|
| GPT-5 | 64% | 21% | 15% |
| Claude Sonnet 4 | 58% | 12% | 30% |
| Gemini 2.5 Flash | 61% | 23% | 16% |

#### Key Observations

- **Higher error rates**: LLMs struggle more with non-standard libraries like `pendulum`
- **Substantial semantic divergence**: High ratio of differentiating to non-differentiating pairs
- **Magnitude of differences**: Most disagreeing pairs differ on nearly all test inputs (not just edge cases)
- **Library understanding gaps**: Models fail to account for library-specific semantics

> **Insight**: LLM-generated code pairs often diverge substantially in semantics when using different date/time libraries. This highlights the need for careful validation when relying on LLMs to generate code in diverse libraries, as models may fail to account for library-specific semantics and edge cases.

### 3. Root Causes of Behavioral Differences

Through manual analysis of 30 differentiating code pairs from GPT-5, we identified five categories of factors contributing to behavioral differences:

#### Category Distribution

| Category | Percentage | Description |
|----------|-----------|-------------|
| **Underspecified Requirements** | 33.33% | Prompts lack information about corner cases and fundamental assumptions |
| **Precision of Representation** | 26.67% | Varying numerical precision across samples (e.g., 3.14 vs 3.14159) |
| **Ambiguous Interface** | 20.00% | Unclear function interface specifications (e.g., return type not specified) |
| **Library Understanding** | 13.33% | Inadequate understanding of library design and implementation details |
| **Lack of Domain Knowledge** | 6.67% | Missing specialized knowledge (e.g., calendar conversion rules) |

#### Example: Underspecified Requirements

**Task**: "Calculate the number of days until the next birthday given a birth date."

**The Problem**: How should February 29th (leap day) birthdays be handled in non-leap years?

**GPT-5 Generated Two Different Solutions**:
- **Sample 1**: Uses February 28th as the birthday observance date
- **Sample 2**: Uses March 1st as the birthday observance date

**Result**: Behavioral disagreement on 0.04% of test inputs due to this single edge case ambiguity.

> **Insight**: Underspecified requirements constitute the predominant source of behavioral differences, accounting for 33.33% of observed inconsistencies. This underscores a critical implication: maximizing the probability of correct date/time code generations requires developers to explicitly articulate corner cases, edge conditions, and fundamental assumptions when formulating prompts for LLMs.

## Development

### Adding New Models

1. Add the model to `ModelType` enum in `genai/models.py`
2. Update the `model_mapping` in `run.py`
3. Add corresponding API key check in `environment_variables_set()`

### Customizing Test Generation

Modify generators in `testing_framework/generators/`:
- `datetime_generators.py` - Hypothesis strategies for datetime objects
- `pendulum_generators.py` - Hypothesis strategies for pendulum objects

### Adjusting Analysis

Customize analysis scripts in `analyze/`:
- `print_diff_test_results.py` - Console statistics
- `plot_diff_test_results.py` - Visualization generation
